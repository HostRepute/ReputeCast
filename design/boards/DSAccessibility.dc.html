Design system · accessibility

WCAG 2.2 AA: what the prototype does, what the build must keep

Every artboard was checked by script: the contrast of every text node against its real background, control boundaries, target sizes, accessible names, landmarks and headings, and reflow at 320px. The failures were fixed in the screens and in the tokens. The table below is the handover checklist for engineering.

What the audit found and changed

Contrast

#5B6472 on #F5F3FF 5.5:1 · public page captions, was #6B7280 at 4.4
#6B7280 on white 4.8:1 · queued rows and muted numbers, was #9AA3B2 at 2.5
#9CA3AF on ink 7.3:1 · code line numbers and comments, was 2.5 and 3.9
warn-bar #B45309 3.8:1 on the track, was #D97706 at 2.8
line-input #8B94A3 3.1:1 input boundary, was #D4D8DF at 1.4
Every other pairing in the token set already passed: body ink 17:1, labels 5.9:1, every badge 5.5:1 or better, links 5:1, white on accent 5:1.

Structure and names

Skip link to #main on every app screen · one h1 per screen, visually hidden where the top bar is a breadcrumb · th scope="col" on 34 tables · 300+ decorative SVGs marked aria-hidden · 66 bare inputs and selects given names (condition field, operator, value; "Map EMAIL to"; "Handling for unsubscribed") · composer canvas and flow canvas exposed as role="main".

Interaction

Global :focus-visible ring · standalone links and the composer title grow to 24px targets · checkboxes 16px with accent colour · links inside sentences underlined · Pause motion control on the landing page and an "Animate flow" switch on the flow canvas (2.2.2) · reduced-motion honoured everywhere · reflow at 320px fixed for badges, buttons, fixed-width cards and the wizard.

Checklist · WCAG 2.2 level A and AA

CriterionStatusHow the system meets it · what engineering must keep
1.1.1 Non-text contentPassIcons are decorative (aria-hidden); icon-only buttons carry aria-label; charts have a table twin; the logo has a text name.
1.3.1 Info and relationshipsPassNative labels wrap inputs; table headers use scope; landmarks header, nav, main, aside; lists are lists. Keep DOM order equal to visual order.
1.3.3 Sensory characteristicsPassInstructions never rely on shape or position alone ("the green button"). Steps are numbered and named.
1.3.4 Orientation · 1.3.5 Input purposePassNo locked orientation. Auth and profile fields carry autocomplete (email, current-password, new-password, name).
1.4.1 Use of colourPassBadges carry words, stat deltas carry arrows, links in text are underlined, errors are text next to the field, chart series are labelled.
1.4.3 Contrast (minimum)PassAudited on all 81 desktop boards after the fixes above: 0 failing text nodes. Keep text on the ink tokens; never set text in a chart or status colour.
1.4.4 Resize text · 1.4.12 Text spacingPassLayouts are fluid; no fixed-height text containers. Verify at 200 percent zoom in the build.
1.4.10 ReflowPassMeasured at 320px: no horizontal page scroll. Data tables, code and the flow canvas scroll inside their card, which the criterion allows.
1.4.11 Non-text contrastPassInput borders 3.1:1, focus ring 5:1, bars at least 3.8:1 on their track, checkboxes use the accent colour.
1.4.13 Content on hover or focusDevTooltips (permission hints, chart tooltips) must be dismissible with Escape, hoverable, and persistent while hovered.
2.1.1 Keyboard · 2.1.2 No trapDevAll controls are native. Drag-and-drop in the composer and flow editor needs the keyboard path: "Add step" buttons on each palette item and an "Insert after" menu on nodes; dialogs trap focus and return it.
2.2.1 Timing adjustablePassSessions warn two minutes ahead with Extend; drafts autosave; toasts with Undo stay 10 seconds and errors stay until dismissed.
2.2.2 Pause, stop, hidePassLanding marquee and flow pulses have a Pause motion control; the app's flow canvas has an Animate flow switch; live counters are content, not decoration.
2.3.1 Three flashesPassNothing flashes; pulses are 1.8s and low amplitude.
2.4.1 Bypass blocks · 2.4.2 Page titledPassSkip link to main on every app screen; every screen has a descriptive title and h1.
2.4.3 Focus order · 2.4.7 Focus visible · 2.4.11 Focus not obscuredPassFocus follows DOM order; 2px ring with offset everywhere; the phone tab bar leaves 72px so focused controls are never under it.
2.4.4 Link purpose · 2.4.6 Headings and labelsDevRow actions repeated per row ("Open", "Manage") must get the row name in aria-label ("Open Welcome series"). Headings describe content, not features.
2.5.3 Label in namePassAccessible names start with the visible text.
2.5.7 Dragging movementsDevEvery drag (blocks, nodes, segment groups, column reorder) has a single-pointer alternative: buttons or menus.
2.5.8 Target size (minimum)PassStandalone controls at least 24px; 36px with a mouse, 44px on touch widths. Inline links in sentences and table checkboxes rely on the spacing exception.
3.1.1 Language of pagePasslang="en" on every document; translated builds set it per locale.
3.2.1 to 3.2.4 PredictablePassNothing changes context on focus or input; navigation and component names are the same on every screen.
3.2.6 Consistent helpPassDocs and Discord links sit in the same place on every screen's sidebar footer and landing header.
3.3.1 Error identification · 3.3.3 SuggestionPassErrors say what is wrong and how to fix it, next to the field, with aria-invalid and aria-describedby; a summary links to each field on submit.
3.3.2 Labels or instructionsPassEvery field has a visible label; format hints sit under the field, not in the placeholder.
3.3.4 Error preventionPassDestructive actions confirm with the blast radius and, for lists and workspaces, a typed name; sends confirm the recipient count; undo where safe.
3.3.7 Redundant entryPassWizards remember earlier steps; invites prefill email; the migration keeps mappings between runs.
3.3.8 Accessible authenticationPassNo puzzles or transcription; passkeys and SSO; two-factor codes accept paste; recovery codes and email fallback.
4.1.2 Name, role, valuePassNative elements; custom pieces (tabs, dialogs, toggles) use the ARIA pattern named in the component spec.
4.1.3 Status messagesDevToasts use role="status", errors role="alert"; the live monitor's counters announce once a minute through aria-live="polite", not on every event.

Audit method · rerun it on every change

Scripted, per artboard

For every text node: computed colour against the nearest opaque ancestor background, alpha blended, measured against 4.5:1 or 3:1 for large text. For every control: bounding box against 24px, presence of a label or ARIA name. Landmarks, h1 count, lang, th scope, bare SVGs, removed outlines. Reflow: every fluid board rendered at 320, 390, 834 and 1440 with the first overflowing element reported.

By hand, before release

Keyboard walk of each flow (sign in, build a campaign, send, pause, resume); screen reader pass on the composer, the flow editor and the live monitor; 200 percent zoom; Windows High Contrast; a colour-vision simulation on every chart.

Out of scope for the prototype

Email templates sent to subscribers (they follow the publisher's brand and the MJML output's own accessibility rules), PDF exports, and the GrapesJS and React Flow runtimes, which ship their own keyboard models and must be configured, not reinvented.

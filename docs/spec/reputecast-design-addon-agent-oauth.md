# ReputeCast — A5: external MCP connections

ChatGPT and Claude may read explicitly granted editorial context and submit durable proposals. Only a signed-in person can apply a proposal in ReputeCast. External connections never invoke the workspace's model, inherit `ai:use`, send mail or publish content.

## Status and scope

This is the separate A5 security and interaction brief required by `reputecast-design-addon-agent.md` §3.8. It extends that approved brief without changing A1–A4 or enabling A6. The owner authorized implementation of A1–A5. The security decisions below are implementation choices; no connection is enabled by writing this document. Real ChatGPT and Claude interoperability remains an acceptance gate, not an inference from passing an SDK test.

The existing token-based `/mcp` and its existing tools remain unchanged. OAuth uses a separate endpoint and an explicit, smaller registry. A token for the new endpoint must fail at `/mcp`, REST API-key authentication and every paid AI endpoint. Existing API keys and MCP tokens must fail at the OAuth endpoint. Reuse domain validators and human draft-acceptance services, not the legacy MCP dispatcher or its contact, sending and settings tools.

## Authorization and identity

- The resource is the configured public origin plus `/mcp/connect`, independent of workspace slugs and incoming Host headers. OAuth discovery, redirects and consent use that same configured HTTPS origin. Permit HTTP only for an explicitly configured loopback development instance; never infer this exception from a proxy header.
- Support authorization code with PKCE S256 and rotating refresh tokens. No implicit, password, client-credentials or plain-PKCE flow. Require the exact resource in both authorization and token requests. Return the issuer parameter in authorization responses and advertise issuer-response support.
- Publish RFC 9728 protected-resource metadata for `/mcp/connect` and RFC 8414 authorization-server metadata. Unauthenticated MCP requests return 401 with `WWW-Authenticate` pointing at resource metadata. Invalid scope returns 403; expired, revoked, wrong-resource or wrong-client tokens return 401.
- Start with RFC 7591 dynamic registration and pre-registration, with `none`, `client_secret_basic` and `client_secret_post` as supported token authentication methods. Generate confidential client secrets on the server and show them once. Do not advertise CIMD, `private_key_jwt`, introspection, OIDC or other unimplemented features. CIMD is not necessary when clients support DCR and introduces arbitrary outbound fetches. No client metadata URL, logo, policy or home page is fetched or rendered as trusted HTML.
- Register only authorization-code/refresh grants, response type `code`, one chosen authentication method and at most five exact HTTPS callback URIs. Permit numeric loopback HTTP callbacks for native clients. Refuse wildcard hosts, fragments, userinfo, protocol-relative URLs, ambiguous encoding and oversized values. Native loopback port matching is the only permitted deviation from exact URI matching; preserve exact host, scheme, path and query. No open redirect on validation failure: show an error locally unless the client and callback were both validated.
- Client registration establishes an identifier, not trusted branding. Consent displays the callback host and “Unverified client” for dynamically registered clients. A claimed client name such as “ChatGPT” is not evidence of identity. Self-hosted operators can pre-register verified client configurations; copying an arbitrary DCR name into an allowlist is not verification.
- An authorization request lasts five minutes. It has a random opaque handle, not a URL carrying permissions, PKCE verifier, recipient data or tokens. Bind the pending consent to the authenticated user/session when they open it. A different session or a consumed request cannot approve it. Re-read the immutable request on confirmation; never accept a callback, client, scope, workspace or resource supplied only by the browser.
- Consent requires a current human session, the instance's existing MFA policy, `mcp:manage` and the selected capability's normal permissions. Choose exactly one workspace; choose list and sender-domain scope within the person's current scope. Show denied capabilities with their missing permission. Do not create a grant, token or product draft when consent is opened or denied.
- A grant is a separate external MCP principal: `ActorMCPAgent`, grant ID, consenting user's `UserID`, frozen granted permissions and scope, client ID and resource. Every call intersects that grant with the user's current active membership, role and scope. A permission downgrade takes effect on the next call; a later upgrade never expands the frozen grant. Never represent an external caller as `ActorUser` to reuse a people-only API.
- Access tokens last ten minutes. The grant and refresh family have a thirty-day absolute expiry; refresh does not extend it. Codes last sixty seconds and are single-use. Store only hashes of opaque codes, access tokens, refresh tokens and client secrets. Use at least 256 random bits for token material, constant-time verification and distinct prefixes. PKCE challenges are bound to the code, client, callback, resource and grant.
- Rotate refresh tokens atomically under a family lock. A correctly authenticated replay of an already-used refresh token revokes the whole family, including its access tokens. Invalid client credentials or a token presented to a different client must not revoke another client's family. Two concurrent refreshes have exactly one winner; a replay response cannot undo revocation. Client-side network ambiguity requires reconnecting, not a grace window that makes refresh tokens reusable.
- Revocation is idempotent and returns no token-existence oracle. A person may revoke their connection; workspace MCP managers may revoke any connection in their workspace. Revoke access, refresh family and pending codes together. Preserve already accepted drafts. Unapplied proposals from the revoked grant become non-applicable, with a readable explanation and a copy-to-editor recovery path for permitted people.
- Allow optional IP/CIDR restrictions using the existing trusted-proxy/IP policy. They apply to MCP calls and refresh, not to the person's consent browser. Show that clients with changing egress addresses can stop working. Changes cannot broaden the grant beyond the manager's own current access.

## Capabilities and model data

Capabilities are OAuth scopes, not new workspace permissions. All require workspace membership and resource scope; all are optional except that at least one must be granted. A tool is absent or denied unless its capability is granted and current domain authorization succeeds.

| OAuth scope | Capability | Domain access | Data boundary |
|---|---|---|---|
| `editorial:read` | Discover and read approved editorial sources | Resource view permission; templates/voice use their existing read gates | Named allowlisted fields, unrendered content, opaque link/token bindings; no recipient lists, sender addresses, public share links or raw errors |
| `reports:read` | Read safe campaign aggregates | `reports:view` plus campaign scope | Fixed totals and periods, small-cohort suppression; no per-person events, links, free-text dimensions, arbitrary filters or generated report-share URLs |
| `drafts:propose` | Submit a new draft or an exact-revision change | Each target's read/edit permissions | Durable staging only; validated MJML/graph/builder content; no product mutation until a human decision |

New drafts may be campaigns, unpublished web posts, builder segments and unpublished automation bundles. Existing changes target only editable drafts; active segments, published posts and live automations are not in-place targets. Existing resource selection uses opaque grant-bound source handles with a saved revision and local bindings. A handle from another grant/workspace cannot resolve. Resource discovery must not copy a contact-derived label, field value or internal ID into model context. Detected personal records and secrets are withheld with a fixed reason. The owner's controlled option 2 permits human-reviewed editorial text with disclosed residual risk: regex matching is not an anonymity guarantee. Require `sharingReviewed: true` for each source selection before creating its handle, and record the `reviewed-editorial-v1` policy in the source-selection audit. OAuth consent alone is not consent to share every readable resource.

There is no scope for contacts, recipient previews, messages, SQL, arbitrary network requests, coupon codes, subscription/suppression changes, settings, routing, send/test-send/schedule, approval or publish. No granted scope makes these tools callable. No external tool may call an AI service, reserve an in-app model budget or execute another external tool.

The initial report projection contains only send dates rounded to UTC days and campaign-wide counts. A campaign must be a completed email send at least 72 hours old. Suppress all counts below 100 sent; release an individual metric only when both it and its complement against sent are at least 20. Round down to tens. Missing metrics are withheld, not zero. No names, links, dimensions, rates or arbitrary filtering are included. The first human selection freezes one shared snapshot per campaign, across grants and runs, so reconnecting cannot reveal later changes. Snapshots expire after 30 days; bounded cleanup removes their counts and retains only a campaign ID/timestamp tombstone to prevent reconstruction. Selections expire after at most two hours and never outlive that snapshot. These controls prevent refresh-based differencing within a campaign, not identification across overlapping campaigns; the privacy acceptance gate must not be represented as a mathematical anonymity guarantee.

The consent and source-selection screens explain that the external client's conversation, storage, model charges, retention and training policies are outside ReputeCast. Before sharing, the person reviews the selected content, confirms authority to disclose it, and sees the remaining prose and cross-campaign inference risks. No confirmation bypasses filters or grants contact tools. Revoking a connection stops future access; it does not delete data already received by ChatGPT, Claude or another client. ReputeCast promises neither zero retention nor no training across all account plans.

## Durable proposals and human decisions

- Create immutable proposal revisions with grant/client/author attribution, target ID and base revision, source snapshot, local bindings, validated staged content, dependencies, status, created time and expiry. A notification is a link to this object, never the approval record itself.
- Require a client-generated idempotency key for proposal creation. Scope it to grant and operation; store its normalized request digest. A retry returns the same proposal, a changed payload with that key returns conflict, and concurrent requests create at most one proposal. A retry never reapplies an accepted proposal.
- A person opens Proposals in the selected workspace. Show client identity, creator, expiry, resources, exact before/after content, validators and dependency impact. New bundles use Keep/Discard; existing changes use Accept/Reject. Distinguish the external client's proposal from an in-app Agent run.
- Decisions use only the normal human session and each resource's current edit permission and scope. Keep/Accept reruns domain validators and checks the grant is active, source scope is still valid, and every target's exact revision is unchanged. Domain writes, history, audit and decision commit atomically. No force, automatic merge or changing a proposed target during acceptance.
- Stale proposals show **Changed since this proposal**. Keep the rejected proposal readable; a fresh source and a new proposal are required. Reject/Discard never deletes an existing target. Repeated identical decisions are idempotent; an opposite decision conflicts. Kept/accepted resources are never deleted on revocation, cancellation or retention.
- Default proposal expiry is the workspace's existing MCP approval expiry (two hours by default), capped by the grant's absolute expiry. Expire application authority exactly at the deadline even if cleanup has not run. Keep readable closed content for seven days, bounded by thirty days from creation; purge staging and bindings after that. Content-free audit follows the existing policy. Instance backups have their own disclosed retention.
- Audit consent, grant creation/revocation, refresh-family reuse, proposal creation and decisions. External requests use the MCP principal; human application uses the deciding user with `via: external_mcp`, grant ID and proposal ID. Record no codes, tokens, prompts, diffs, generated content or free-text client arguments in logs, audit, analytics or notification emails.

## Performance and abuse controls

Use indexed token hashes, proposal status/expiry indexes and keyset pagination. Do not scan every grant to authenticate. No transaction spans a network call. Discovery is static and cacheable; token, authorization and consent responses are `no-store` with `Referrer-Policy: no-referrer`. Consent cannot be framed and loads no third-party content.

Use database-backed registration/authorization rate counters shared across replicas, plus the server's existing per-network abuse protection. Start at ten registrations and thirty pending authorizations per network per ten minutes; never allow unbounded pending rows. Expire unused dynamically registered clients after seven days; retain a client while its unexpired grants require it. Apply a per-grant MCP rate limit and bounded concurrency, request size, output size, query timeout and proposal count. Return 429 with `Retry-After`; do not silently queue unlimited work. Cleanup runs in bounded batches with `SKIP LOCKED`.

## Screens and interaction

`MCPConnect` contains the consent, connection management, proposal review and blocked-state prototypes. It extends Settings › Keys & MCP without replacing legacy token setup. The same layout reflows at 1440, 834 and 390 pixels, with light/dark tokens, keyboard-visible focus and phone targets of at least 44 pixels.

- Consent: unverified/verified identity distinction; callback host; workspace; optional capability checkboxes; scope summary; expiry; explicit external-data disclosure; Deny and **Allow connection**. Narrow screens stack rather than truncate permissions or actions.
- Connections: client, consenting person, workspace, granted capabilities, resource/IP scope, expiry, active/revoked status and Revoke confirmation. Never display bearer or refresh tokens.
- Proposals: separate new bundles and existing changes; before/after, plain-language consequences, expiry, validators and human confirmation; no Send or Publish shortcut.
- States: invalid request without redirect, sign-in/MFA required, missing permission, expired request/grant/proposal, revoked connection, stale revision, refresh reuse, rate limiting and offline submission with a safe status recheck. Browser Back/reload cannot approve twice.

## Acceptance gates

1. Real HTTP OAuth discovery → DCR or pre-registration → consent → code/PKCE → MCP → refresh → revoke, against disposable Postgres. Also test both supported confidential-client authentication methods. Do not use a test helper that bypasses bearer verification or consent middleware.
2. Reject tampered state/callback/resource/client/PKCE, duplicate parameters, expired/reused codes, replayed refresh, arbitrary redirect URLs, token substitution between legacy MCP/REST/OAuth, and consent from a different session. Assert database grants and token families, not just status codes.
3. Two processes race a code exchange, refresh and proposal key; only the authorized transaction wins. Revoke or remove membership during a request; no later read/write succeeds. Client registration and pending requests remain bounded under repeated and concurrent attempts.
4. Durable proposals survive process restart. An existing draft edited by a person rejects the old diff. Double acceptance does not add another version. Expiry/revocation makes a pending proposal non-applicable. Keep of a dependency bundle creates no messages, live version, memberships or automation runs.
5. Run the A3 privacy/injection fixtures through every external tool. Missing or false sharing confirmation must create no source handle; reviewed valid content must still work, while detected personal records remain rejected. Assert zero calls to the in-app model and unchanged budget/usage tables. Check content and token sentinels are absent from logs, errors, notifications and audit.
6. Exercise consent, denial, revoke, review and stale/offline states with keyboard and pointer, five locales, light/dark, desktop/tablet/mobile layouts, 320px overflow checks and axe. Test touch with a coarse-pointer browser profile; do not label Chromium emulation as a real phone.
7. Complete a real connection, reconnect, scope denial and proposal review from both ChatGPT and Claude's supported remote-MCP clients. Record client/version/date and redirect-registration mode. Owner sign-in and a reachable HTTPS installation are required; do not enable a public deployment or use paid model accounts without authorization. Until this is done, describe interoperability as unverified.

## Implementation ownership

OAuth transport, grant/token lifecycle and external tool dispatch belong in `internal/mcpconnect`; they do not change `internal/api` authentication semantics or add permissions to `internal/authz`. Wiring belongs in `internal/app/wire_mcpconnect.go`; queries in `internal/store/queries/mcp_connect.sql`; reserve migrations 03620–03629 when implementation begins. Reuse current domain proposal services, adding actor-safe staging interfaces where needed rather than weakening human-only acceptance. UI belongs in `web/src/features/mcpconnect`, with thin routes and generated API types.
